# SSE 流式响应里那些没人告诉你的坑

写于 W2 Day 7（2026-10-14）。所有数字都是本项目实测的，每个结论后面都附了可复现的脚本或命令。
凡是我没实测过的，会明确写成"没验过"。

先说结论：**SSE 的协议简单到能写在餐巾纸上，但"能跑通"和"生产上真的逐字到达"之间隔着七八道坎。
这些坎的共同特征是——它们不报错。** 它们只是让流悄悄变成"一次性到达"，或者让日志里少几行，
或者让首字延迟从 0.3 秒变成 2 秒。没有异常、没有 500、测试还是全绿。

---

## 坑 1：`TestClient` 会把整段响应缓冲掉，于是时序断言全是假的

这是本项目最容易被误判的一个坑。

在 `TestClient` 里 `iter_lines()` 读 SSE：**帧内容和顺序完全正确，但首帧 0.000s、末帧也是 0.000s。
所有帧的时间戳都是 0。** 因为 TestClient 走的是 ASGI 直调，不经过真实网络栈，整个响应被一次性构造完再交给你的迭代器。

真实 HTTP 实测（`scripts/probe_stream_timing.py`，服务需先起）：

```
帧数 89 · 首帧 0.002s · 首末帧间隔 2.80s · ttft_ms=28
```

**规矩：内容和顺序用 TestClient 断言（快、稳、能进 CI）；时序必须打真实 HTTP。**
这两层不是重复劳动，它们回答的是不同问题。

同一个陷阱在 WebSocket 上又应验了一次：未授权的握手被拒，`TestClient` 抛 `WebSocketDisconnect`，
而真实客户端拿到的是 **HTTP 403**（`InvalidStatus`）。**同一个行为，两种表现。**
所以 `scripts/ws_client_demo.py`（真实 `websockets` 客户端）和 TestClient 测试必须并存。

## 坑 2：`data` 里带换行，必须**每一行**都加 `data: ` 前缀

SSE 的帧结构是「若干 `字段: 值` 行 + 一个空行收尾」。空行是帧分隔符，
所以一条 `data:` 只能承载一行文本。

如果直接把带换行的内容塞进去：

```python
# 错：客户端只收到第一行，后面全部丢失——而且不报错
f"data: {text_with_newlines}\n\n"

# 对：每一行都加前缀，客户端用 \n 拼回
"".join(f"data: {line}\n" for line in text_with_newlines.splitlines())
```

最阴的地方是**它静默丢数据**。模型回答里有换行（代码块、列表）时，用户看到的答复被截断了，
而服务端日志里一切正常。本项目 `sse_frame()` 里专门处理了这个分支，`scripts/demo_sse_protocol.py` 可以复现。

顺带一条同源的：**以 `:` 开头的行是注释**（常用于心跳保活），客户端必须忽略。
它的作用是防止中间代理/网关把「长时间没有数据」判定成超时。本项目定期发 `: ka`。

## 坑 3：`X-Accel-Buffering: no` —— 它到底在哪种部署形态下才起作用

这条悬了好几轮，这里正面回答。

**它不是一个 HTTP 标准，是 Nginx 家族的约定。** Nginx（以及派生品，如 Kubernetes 的 ingress-nginx）
认得这个响应头，作用是**针对这一个响应**关掉 `proxy_buffering`。

Nginx 默认 `proxy_buffering on`：它会把上游（我们的 uvicorn）的响应**攒在自己的缓冲区里**，
攒够或者响应结束再发给客户端。对普通 JSON 响应这是优化；对 SSE 是灾难——
token 明明一个个产出了，用户那边仍是「等了半天，一次性全出来」。SSE 的意义直接归零。

**它在这些形态下才起作用：**

| 部署形态 | 起作用吗 |
|---|---|
| 客户端 → Nginx `proxy_pass` → uvicorn（裸机 / 虚机） | ✅ 这就是它存在的理由 |
| 客户端 → ingress-nginx → Pod（Kubernetes） | ✅ 同类机制 |
| 客户端 → uvicorn（本机开发） | ❌ no-op，没有代理 |
| 客户端 → `docker run -p 8000:8000` → uvicorn | ❌ no-op，端口映射是纯转发 |
| 客户端 → 某云 LB / CDN → 应用 | ⚠️ **不一定认**。它不是标准，换网关必须重新验证 |

**症状特征：本地好、线上不好。** 这正是它难查的原因——你的开发机上根本没有 Nginx，
本地怎么测都是好的。而它和坑 7 正好方向相反，排查时先问一句
**「这个差异是在链路的哪一端产生的」**，能省掉大量瞎猜。

**本项目的做法：无条件带上这个头。** 在没有 Nginx 的环境里它是几字节的 no-op，
在有 Nginx 的环境里它救命。让代码不依赖部署形态，比让运维去调 Nginx 配置可靠得多。

⚠️ 但要清楚它的边界：**这类问题测试永远测不出来。** 它和 Day 6 那个
`setup_logging()` 从不被调用是同一类——**只存在于部署形态里的问题**，
只能靠读真实产物或靠部署知识发现，任何单测都覆盖不到。

## 坑 4：SSE 协议里**没有**「结束标记」这回事

规范只定义了三样东西：字段（`event` / `data` / `id` / `retry`）、注释、空行分隔。
**没有「流结束了」这个语义。**

服务端关掉响应体，客户端只能得到 `onerror` 或 `readyState=CLOSED`——
也就是说，**客户端分不清「正常答完了」和「网络断在半路」**。

更要命的是浏览器的 `EventSource`：**它会把正常关闭也当成失败，然后自动重连**（默认约 3 秒后）。
于是「已经答完了」被理解成「断了」，客户端反复重连，服务端反复重放。

所以每个实现都自己发明一个约定：

| 实现 | 结束标记 |
|---|---|
| OpenAI Chat Completions | `data: [DONE]` |
| 本项目 | `event: done`（自定义事件名） |
| 另一种常见做法 | 最后一个帧带 `finish_reason` / `usage` |

**自己约定的代价**：客户端必须知道你的约定，没法指望「按规范总不会错」。
**好处**：可以携带结束元信息（finish_reason、token 用量、总耗时），这是单纯靠「关连接」做不到的。

断线重连本身倒是有协议支持：服务端发 `id:`，浏览器重连时会自动带上 `Last-Event-ID` 请求头。
但**「从哪个位置继续」要你自己实现**，协议只负责把 id 送回来。

## 坑 5：你的「流式」可能是**传输层真、生成层假**

W2 的占位模型是这么写的：`build_reply()` 先返回**完整字符串**，再靠 `tokenize()` 里的
`sleep` 一个个放出去。

结果是：**发出第一个 token 之前，整段回复已经生成完毕了。** 传输层是逐帧的（真的），
生成层是一次性的（假的）。

同一份模型成本下实测（`scripts/probe_real_vs_fake_streaming.py`）：

| | 首字延迟 TTFT | 总时长 |
|---|---|---|
| 假流式 | **2.11s** | 更长 |
| 真流式 | **0.30s** | — |

首字延迟差 **约 7 倍**，总时长还多出 1.79s——因为生成时间被付了两遍：
先完整生成一遍，再按节奏「播放」一遍。

（数字取自 README「已知限制」里记录的那次测量。不同次运行会有约 0.05s 量级的抖动，
所以你自己跑出来可能看到 0.31s / 1.76s 之类的值——**倍数量级是稳的，小数位不是。**）

**为什么本地看不出来**：占位模型瞬间返回，`build_reply` 耗时≈0，两种实现看起来一模一样。
只有接上真实模型（要花 2 秒生成）才会暴露成「用户盯着空白屏幕 2 秒」。

**教训：返回类型决定能力边界。**

```python
def build_reply(...) -> str: ...                    # 从签名上就不可能真流式
async def stream_reply(...) -> AsyncIterator[str]: ...  # 这个才是
```

W3 接真实模型时必须**拆成两个入口**，而不是替换一个——`streaming.py` 和 `ws.py` 各有一处调用点要改。
我最初在本项目注释里写的「签名不变、上层一行都不用改」是**错的**，已改正。

## 坑 6：浏览器的 `EventSource` 设不了自定义请求头

`new EventSource(url)` **没有 headers 参数**（`WebSocket` 构造函数也一样）。

所以如果服务端要求 `X-API-Key`，浏览器这条路直接走不通。现实的三个选择：

1. **凭据放查询参数** `?api_key=xxx` —— 能跑，但**会进访问日志**（和 URL 一起被记下来），
   需要注意日志的留存与脱敏。
2. **首帧消息里带凭据** —— 不污染日志，但握手阶段无法鉴权。
3. ✅ **不用 `EventSource`，改用 `fetch()` + `ReadableStream` 手工解析 SSE 帧** ——
   `fetch` 能设任意请求头。代价是自动重连、`Last-Event-ID` 全得自己写。

第 3 条是真正的解法。**这是「SSE 比 WS 省事」这条结论的一个明确例外**，
也是面试里值得主动说出来的点——说明你知道那条结论的边界在哪。

## 坑 7：Windows 上 `asyncio.sleep` 会被向上取整

`scripts/probe_sleep_granularity.py` 实测（可复跑，退出码 0）：

| 传入 | 实际睡了 | 相当于几个刻度 |
|---|---|---|
| 1ms | 15.2ms | 1 |
| 5ms | 15.0ms | 1 |
| 20ms | 30.2ms | 2 |
| 50ms | 61.9ms | 4 |
| 100ms | 108.3ms | 7 |

规律很清楚：**实际耗时向上取整到约 15.6ms 的整数倍**（Windows 的定时器刻度是
15.625ms = 64Hz，即经典的一「tick」）。脚本用网格拟合反推粒度：**三次独立运行
分别得到 G ≈ 15.39 / 15.59 / 15.54ms**（全域最大偏差 0.38 ~ 0.58ms），
五个测量点全部吻合，且都紧贴 15.625ms。

对照实验：同一台机器上 `time.sleep` 是准的（1ms→2.0ms、20ms→20.7ms、100ms→100.5ms，
偏差 1% 以内）。**所以这是【事件循环定时器】的问题，不是操作系统做不了精细睡眠。**

所以本项目 `.env` 里 `STREAM_DELAY_MS=20`，本机实际节奏约 **31ms/token**。
**「实测 31ms」和「配置 20ms」两个数都对**，只差一个「原来没追究差值」的步骤。
顺带说明：不同次运行会有约 1ms 的抖动，所以你在自己机器上跑出来的数可能和上表差一点，
但「整数倍」这个规律是稳的。

影响面不止流式：将来做**重试退避、心跳周期、限流窗口**时，每次都会多睡最多一个刻度（~15.6ms），
在短周期场景下会累积成可见偏差。

⚠️ 方向提醒：这是**本地坏、线上好**（Linux 无此问题），跟坑 3 正好相反。
两个坑放在一起看，就是那条通用判据：**先确定差异产生在链路的哪一端。**

## 坑 8：`curl` 自己会缓冲，验收必须加 `-N`

```bash
curl http://127.0.0.1:8000/chat/stream          # ❌ 可能一次性吐出全部
curl -N http://127.0.0.1:8000/chat/stream       # ✅ -N = --no-buffer
```

不加 `-N` 时看到「一次性到达」，**那是 curl 的缓冲，不是服务端的错**。
很容易照这个假象去改服务端代码，白改半天。

## 附：本项目实测**否掉**的一个流行说法

> 「`BaseHTTPMiddleware`（`@app.middleware("http")`）会破坏流式响应的时序。」

`scripts/probe_middleware_vs_sse.py` 做了三方对照——**不加中间件 / 纯 ASGI 中间件 / `BaseHTTPMiddleware`**，
在 starlette 1.7.0 上测：

| 指标 | 结果 |
|---|---|
| 帧数 | 三者一致（66 token 帧 / 68 总帧） |
| 首字延迟 TTFT | 0.12 ~ 0.14s，无可观测差异 |
| 总时长 | 4.16 ~ 4.19s，无可观测差异 |
| token 间隔 | 59 ~ 75ms，无可观测差异 |

**在这个项目里，这条说法不成立。**

本项目最终仍然选了纯 ASGI 中间件，但**理由改了**：职责清晰、少一层不可见抽象。
不再假装是性能原因。

⚠️ 另外记一笔方法论错误：这个脚本**第一次跑时基线（不加中间件）反而最慢**（TTFT 0.905s），
差点得出「中间件居然更快」的荒谬结论。原因是**冷启动被错误归因**——第一个被测的方案替所有方案
付了进程启动成本。加了预热调用并丢弃结果后，基线降到 0.120s。
**以性能为名做选择时，先把性能量出来；量的时候先排除冷启动。**

能证伪它们的只有一样东西：**去读真实跑出来的东西。**
